# src/weapons — Weapons, grenades, weapon FX

Owner: `WeaponSystem` (`name: 'weapons'`). Registers after `PlayerSystem`; reaches the player through `ctx.player` narrowed to `PlayerRef & PlayerWeaponHost`.

| File | Purpose |
|---|---|
| `WeaponSystem.ts` | Slots primary/secondary from `loadout:changed` (defs via `ctx.loot.getItemDef(defId).weaponId → getWeaponDef`, fallback built-ins). Ammo (`ammoInMag`, `reserveRounds`) persisted per item `uid` so swapping keeps state. LMB fire (auto/semi, only while pointer-locked and `host.canUseWeapons()`), R reload (empty reserve → `inventory.consumeWhere(ammo of def.ammoType)` refills `reserveMags × magSize`, else "탄약 없음"), **1/2/V** swap with a 0.4 s holster/draw (halved by the 전술 가방 perk), G grenade (`consumeWhere(grenade)`), **F melee** (delegated to `Melee.ts`). Firing: reticle ray from `host.getAimRay` with spread = lerp(hip, ADS) × **stance table** (`STANCE_ACCURACY`: stand-hip 1.0 / stand-ADS 0.7 / crouch 0.55 / 0.4 / prone 0.32 / 0.22, read from `host.stance`) × bloom × moving 1.35 / sprinting 1.5 → nearest of `enemies.raycast`/`world.raycast` (hits between camera and player ignored) gives the target; the real shot is re-cast from the muzzle toward that target; tracer from muzzle; damage × `damageFalloff(def, muzzle→hit distance)` (linear 1 → `falloffMin` between `falloffStart`/`falloffEnd`); `enemy.takeDamage(dmg, point, dir)`; shotgun pellets (falloff per pellet); `projectileSpeed` weapons use `ProjectilePool` (falloff from `ProjectileHit.distance`). Recoil = `def.recoil × stance multiplier` → `host.addRecoil`. **SR (bolt-action)**: after each shot a bolt-cycle phase (`1/fireRate − 0.05 s`) blocks the trigger, drives `WeaponModel.setBolt(t)` and emits `audio:play bolt_cycle` 0.22 s after the shot; extra `camera:shake`. **ADS zoom**: `applyAimZoom` calls `host.setAimZoom(def.adsZoom ?? 1, !!def.scope)` + emits `weapon:scopeChanged` on equip / swap / unequip and `(1,false)` on `world:ready`/`game:abort` (de-duplicated). `twoHanded` = class ≠ PISTOL. No firing while `host.isDiving`. Emits `weapon:equipped/ammoChanged/fired/dryFire/reloadStarted/reloadFinished/hit/scopeChanged`, `ui:hitmarker {kill, headshot}` (headshot = `EnemyHit.part === 'head'`), `grenade:countChanged`, `audio:play`. Pose → `host.setWeaponState`. If no `loadout:changed` arrives within 1 s of `world:ready`, equips the built-in rifle + pistol. **Multiplayer**: sends `fire` / `reload` / `grenade` messages (see below) and owns a `RemoteWeapons` instance that it updates every frame and clears on reset. |
| `Melee.ts` | `MeleeController` (owned by `WeaponSystem`). F / `KEY_MELEE`: asks `ctx.player.startMelee()` — the **player** owns stamina (`MELEE_STAMINA_COST`), `MELEE_COOLDOWN` and the swing pose — and only on `true` queues a `MELEE_WINDUP` (0.16 s) resolution. Damage = `MELEE_DAMAGE × (WeaponDef.meleeMul ?? MELEE_STOCK_MUL_DEFAULT) × derived.meleeDamageMul`, so every weapon hits the same except stocked (개머리판) primaries. Hit test: cone from the eye position along the aim ray, `MELEE_RANGE` + target radius, cos half-angle 0.34 (~70°), up to 4 targets — enemies (`ctx.enemies.queryNear`, falling back to `getEnemies()`) via `EnemyRef.takeDamage` and deployables via `DeployableRef.takeDamage`. Emits `melee:swing` (once, guarded so its own listener never double-resolves — if `player/` reads F first and emits `melee:swing`, this resolves *that* instead), `melee:hit` per contact, `ui:hitmarker`, `camera:shake`, `audio:play melee_swing`/`melee_hit`. Multiplayer: `{ t:'melee', p, d, hit }` to others (FX only); enemy damage rides the existing client → host `hit` request inside the replica's `takeDamage`. |
| `Blocking.ts` | `raycastBlockers(ctx, origin, dir, maxDist, out, fromEnemy=false)` → distance of the nearest shield / solid deployable on the segment or -1. Consults `ctx.implants?.raycastBarrier` and `ctx.gadgets?.blocksProjectile`, both optional and wrapped in try/catch (those systems may not be registered yet). Allied barriers only stop **hostile** projectiles, so player bullets pass through them; barricades / dome hulls are physical and do stop friendly fire. Used by `WeaponSystem.raycastAll` (hitscan, both the camera and the muzzle ray) and by `ProjectilePool` per sweep step. |
| `WeaponDefaults.ts` | `DEFAULT_RIFLE` (AR-23 리버레이터, class AR, falloff 60→220 ×0.6), `DEFAULT_PISTOL` (P-2 피스메이커, class PISTOL, falloff 20→70 ×0.5) fallbacks; `kindOf(def)` → rifle/pistol/shotgun/energy/**smg**/**sniper** (via `weaponClassOf` from `@/items`, re-exported with `damageFalloff`); `shotSoundId(kind)`; `shotPitchFor(class)` (DMR 0.78); `STANCE_ACCURACY` table. |
| `WeaponModel.ts` | Procedural rifle / pistol / shotgun / energy-rifle / **SMG** (compact receiver, shrouded stub barrel, skeleton stock, vertical mag) / **sniper** (long heavy barrel + brake, scope tube with emissive lens rims and turrets, folded bipod, long stock with cheek riser, bolt handle) meshes (grip at origin, barrel -Z) with `muzzle` and `ejectPort` sockets on every variant. Animation: recoil kick (`kick`), reload (mag drops, disappears, new mag slides in; weapon cants), draw/holster swing (`setDraw`), bolt cycle (`setBolt(0..1)`: handle lifts, pulls back, returns; weapon cants), energy glow pulse. |
| `RemoteWeapons.ts` | **Multiplayer only** (every entry point returns immediately unless `ctx.isMultiplayer && ctx.net`). Owned by `WeaponSystem`. (1) **Remote weapon models**: each frame walks `ctx.net.getRemotePlayers()`; when `ref.weaponId` or `ref.avatar.weaponSocket` changes it disposes the old `WeaponModel` and parents a new one (def via `ctx.loot.getWeaponDef`, fallback `DEFAULT_PISTOL`/`DEFAULT_RIFLE`) into the avatar's socket with identity local transform (same convention as the local `getWeaponSocket()`); kept while `DEAD`; swept when the ref disappears, removed on `net:remotePlayerRemoved`, cleared on `game:abort` / `game:newMission` / `world:ready`. `getMuzzleWorld(id, out)` exposes the model's muzzle. (2) **Replicated fire** (`onFired` ← `net:remoteFired`): muzzle = remote model muzzle if attached else message origin; muzzle flash + tracer(s) via the shared FX pools; visual-only hit test (`enemies.raycast` → `world.raycast`) for impact sparks/dust/ichor — **no damage, no `weapon:hit`, no `weapon:fired`, no hitmarker**; shotgun fans `pellets` rays with the def's hip `spread`; `projectileSpeed` weapons spawn `ProjectilePool.fire(..., visualOnly=true)` (impacts routed to `onVisualProjectileHit`); model `kick`, casing, SR bolt cycle animation + delayed `bolt_cycle`; shot sound via `audio:play {id: shotSoundId(kind), position: muzzle, pitch: shotPitchFor(class)}`. Rate-limited per peer with a token bucket (20 FX/s, burst 6). (3) `onReloaded` ← `net:remoteReloaded`: drives `WeaponModel.setReload` over `def.reloadTime`, `audio:play reload` at the remote's chest, `reload_done` when finished. (4) `onGrenade` ← `net:remoteGrenade`: `GrenadeManager.throw(p, v, visualOnly=true)`. |
| `Grenade.ts` | `GrenadeManager`: 8 pooled frags; gravity, terrain bounce (restitution/friction via `getNormalAt`), obstacle push-out, 2.5 s fuse with accelerating LED blink (emissive LED + one pooled `FlashPool` pulse per blink rising edge via `WeaponFx.ledBlink`); explosion radius 6 m / 250 dmg via `enemies.applyExplosion`, self-damage with falloff, distance-scaled `camera:shake`, `grenade:thrown/exploded`, `audio:play explosion`. **No per-grenade lights** (see "Grenade hitch" below). `throw(origin, velocity, visualOnly = false)`: a **visual-only** grenade (remote player's replica) keeps the arc/bounce/fuse/LED/explosion FX/`camera:shake`/`audio:play grenade_throw|grenade_bounce|explosion` but skips `applyExplosion`, local player damage, `ui:hitmarker` and the `grenade:thrown/exploded` events (so enemies don't "hear" it and audio isn't doubled). When the pool is full a visual-only replica is evicted before a live local grenade. |
| `Projectile.ts` | `ProjectilePool`: 48 swept projectiles (enemy + world raycast per step, slight drop), glowing tracer trail, hit callback with `ProjectileHit.distance` (meters travelled from the muzzle, for falloff). `fire(..., visualOnly = false)`: visual-only slugs (remote replicas) route their hit to the optional second constructor callback `onVisualHit(h, weaponId)` instead of the damage callback. |

## Tactical kit (2026-09-05)

Every hook below is **optional at runtime** — `ctx.progression` / `ctx.implants` / `ctx.gadgets` and the new
`InventoryRef` members are published by systems that may not be registered yet, so each read is
`?.`-guarded with a neutral default (multiplier 1, no block) and cross-system calls sit in try/catch.

## Holster outside gameplay (ship hub)
While `ctx.phase` is `hub`, `docking` or `menu` the WeaponSystem is **holstered**: the attached `WeaponModel.root` is forced invisible every frame, `host.setWeaponState({hasWeapon:false, …})` poses the soldier unarmed, ADS zoom is reset to `(1,false)`, and `resetTransient()` runs on entering (grenades/projectiles/FX cleared, reload cancelled). `hub:entered` also clears transients. Slots and ammo are kept, so the loadout re-appears automatically when the phase returns to `deploying`/`playing` (`attachActive(false)` re-applies the zoom). Firing/reload/swap/grenade input already requires `isGameplayActive()`. `RemoteWeapons` hides a remote's model when its flags carry `IN_HUB`, `IN_POD` or `DROPPING`, or lack `HAS_WEAPON`.

## Grenade hitch (fixed 2026-09-05)
**Root cause**: every pooled grenade carried a `THREE.PointLight` inside a group whose `visible` was toggled. A change in the number of visible lights changes every lit material's program cache key, so three.js recompiled **all** lit shaders (14 programs here) on every throw and again on every explosion — and because the old programs are released when a material switches, this repeated on every single throw (programs 35 → 49 → 63 → 77 …).
**Fix**: grenades have no light; the LED pulse and the explosion flash use the shared `FlashPool` (6 lights permanently in the scene, constant count). Plus a one-shot `warmUp` shader compile during the hellpod drop so hidden FX meshes (rings, flash sprites, grenade bodies, decals) never compile on first use.
**Measured** (headless Chrome, ANGLE D3D11, 800×450, `__game.frame()` wall time; idle p50 2.6 ms, max ≤ 6 ms):

| | throw #1 | throw #2 | 2 concurrent | programs |
|---|---|---|---|---|
| before | **1064 ms** frame (throw) | **1367 ms** | **1203 ms** | 35 → 49 → 63 → 77 |
| after | 5.7 ms max | 5.5 ms max | 5.6 ms max | 64 → 64 → 64 → 64 |

(SwiftShader software GL showed the same pattern with 1.7–2.3 s stalls before, and no throw/explosion-frame spike after.) The bench script lives outside the repo (`scratchpad/grenade-bench.mjs`); it drives a single-player mission and calls `getSystem('weapons').grenades.throw()`.

## Multiplayer (WebSocket relay, host-authoritative)

Every network branch is gated on `ctx.isMultiplayer && ctx.net`; offline behaviour is byte-for-byte unchanged.

**Outbound** (`WeaponSystem`, local player only):
- `fire()` → after `weapon:fired`: `ctx.net.send({ t:'fire', w: def.id, o: muzzle, d: dir })` — one message per trigger pull (shotguns included; the receiver fans out pellets). `d` is the exact muzzle→target line for single shots, the aim centre for pellet weapons. Tuples rounded to 3 dp (`toTuple`).
- `tryReload()` → `{ t:'reload', w }` at reload start.
- `throwGrenade()` → `{ t:'grenade', p, v }` with the same origin/velocity handed to the local `GrenadeManager`.
- `MeleeController.resolve()` → `{ t:'melee', p, d, hit }` after the windup (`p` = swing origin, `d` = aim direction, `hit` = anything was struck). Enemy damage is **not** in this message: it travels the normal `hit` request path inside the replica's `takeDamage`.

**Inbound** (`RemoteWeapons`, via NetSystem's bus events `net:remoteFired / net:remoteReloaded / net:remoteGrenade / net:remotePlayerRemoved`, plus a direct `ctx.net.onMessage('melee')` subscription set up by `WeaponSystem.ensureNet()` → `RemoteWeapons.onMelee` for the swing arc and swoosh/contact sounds) — see the table row above. All of it is presentation: the existing `enemy.takeDamage` / `applyExplosion` path is untouched here; on non-host clients the enemies module forwards those to the host.

**Known limitations**
- Remote players' grenades are visual-only on every other client: they never damage the local player (no friendly-fire), and their enemy damage comes only from the thrower's own client via the host.
- Remote gunfire does not emit `weapon:fired`, so on the host enemies do not "hear" other players' shots (`EnemySystem.alertHearing`); wire that through `net:remoteFired` in enemies if wanted.
- Remote reload animation runs on the receiver's clock from the `reload` message (not from `PlayerFlags.RELOADING`), so a cancelled reload (swap) on the sender still plays out visually.
- Remote melee is presentation only: it never damages the local player and never touches deployables, and the arc is drawn at the sender's swing origin (no interpolation back to the avatar's hand).
- Melee never wears weapon durability (only shots do) and is not blocked by shields/barricades — the cone test ignores line of sight.
